01

Problem & scope

Context

A researcher wants to build and refine a literature search over Europe PMC without learning its query syntax, then read and page through the results. The prototype has two halves and a short list of things it deliberately does not do.

Half A
Query builder. Enter a keyword or phrase. Combine terms with AND / OR / NOT. Show the query as it is constructed. Remove terms and refine.
Half B
Results explorer. Fetch matching publications. Show title, authors, year, article link. 25 per page, next / previous. Loading, empty and error states, accessibly.
Graded on
Functional correctness · maintainable components & clear state · async handling · tests for query construction, navigation, API failure · how work is prioritised.
Hard constraint
~3 hours. A well-reasoned partial beats a feature-complete app that can't be explained. A follow-up interview walks the code and may ask for a live change.

In scope, out of scope

Query builder Results list Next / prev Loading · empty · error Accessibility Tests Facet rail Sort control Abstract detail view
Why the facet rail is a stretch goal, not coreprioritisation

Europe PMC's own results page carries a left rail of filters — free full-text, article type, date — and a relevance / date / cited sort. They are useful, and the design leaves room for them. But the brief asks for the query builder, results and pagination; it does not ask for facets. In a three-hour exercise the clearest way to over-scope is to build what wasn't asked for while the graded core is still thin. So facets sit behind the core and ship only if time remains. This choice is itself part of what's being assessed: the brief names prioritisation twice.

API model

Verified live

Every value below was confirmed against the live endpoint, not recalled. The findings here shape the architecture that follows — above all the shape of pagination.

endpoint

GET https://www.ebi.ac.uk/europepmc/webservices/rest/search
      ?query=cancer AND immunotherapy NOT melanoma
      &format=json
      &pageSize=25
      &cursorMark=*            // "*" for the first page
// No auth, no backend, CORS-friendly for a browser app.
ParamRoleVerified behaviour
queryBoolean search stringAND/OR/NOT applied literally. Hit count fell 5,670,102 → 280,474 when AND immunotherapy NOT melanoma was added, so operators really filter.
pageSizeResults per page25 — matches the brief exactly.
cursorMarkPagination token* first; thereafter the nextCursorMark from the previous response. Forward only.
resultTypeField depthlite (default) returns title, authorString, pubYear, id, source — enough for the list. core adds authorList + abstract for a later detail view.

response — trimmed to what the list consumes

{ "hitCount": 280474,
  "nextCursorMark": "AoIIQEV1pCg1Njk3NTY2Nw==",   // feed back to get the next page
  "resultList": { "result": [
    { "id": "42888301", "source": "MED",
      "title": "…", "authorString": "van Meenen DMP, Hemmes SNT…",
      "pubYear": "2026", "doi": "10.1007/…", "pmid": "42888301" }
  ] } }
The decisive finding

Pagination is a forward-only cursor. The response gives a nextCursorMark; there is no previous cursor and no page or offset parameter. "Previous" navigation therefore has to be a client concern. Section 04 draws the mechanism.

Error reality — the API accepts bad inputshapes the error test

Observed: an empty query returns HTTP 200. A malformed query (an unbalanced parenthesis, cancer AND (immuno) also returns HTTP 200 with results. So the API will not hand back a clean 4xx for a bad query.

Consequence: genuine failures are network failures — a rejected fetch, a non-2xx response, a timeout. The error state and its test are built around those, not around the API rejecting a query. An empty or whitespace query is caught on the client before a request is ever made.

Building the article linkper result

Each result carries source (e.g. MED, PMC, PPR) and id. The canonical public URL is https://europepmc.org/article/{source}/{id} — e.g. europepmc.org/article/MED/42888301. The list links each title there, opening in a new tab.

Structure

The split that matters: the build-* helpers are pure, one per file, so the builder's logic is verified by calling them directly — no React, no network. status-view is one part driven by a status prop, not three near-duplicate blocks. ResultRow takes a plain article object as a Readonly props interface and renders no logic, so it is trivial to test and to restyle. No component calls fetch; data flows only through the api/ hook.

Standards this build followsteam persona
  • Feature-Sliced Design — one article-search feature, shallow nesting since there is a single screen.
  • Tailwind only, EMBL brand tokens in tailwind.config; conditional classes through cn().
  • meemaw <Show> / <Repeat> instead of && and .map().
  • Icons via the @icons proxy (lucide-react), never emoji, never a direct import.
  • No any; every component's props are an externalised Readonly<…Props> interface.
  • React Query only for server state; zero bare useEffect + fetch.
  • Endpoints via EP constants, no inline URLs; hyphenated filenames; a feature-boundary barrel only.
  • Inline errors over toasts.
  • Shared utilities, not inline logic — number formatting and other cross-cutting helpers live in shared/utils (e.g. formatNumber), never re-created per component.
  • oxlint + Prettier run clean across the codebase; reusable UI (Button, Chip, TextField, SegmentedControl, StatusMessage, Logo) lives in ui/ and is composed into the feature.
04

Pagination mechanism

The hard part

The API moves only forward, one cursor at a time, yet the brief wants discrete next and previous pages of 25. The resolution: fetch forward, navigate backward through the cache. TanStack Query's useInfiniteQuery is built for exactly this cursor shape.

Forward fetch, backward navigation — a page pointer over cached pages
Cached page (instant) Fetched on Next Page pointer

Rules the hook enforces

  • Next: if the next page is already cached, move the pointer forward; otherwise call fetchNextPage(), which sends the stored nextCursorMark.
  • Previous: decrement the pointer. The page is always already cached, so there is no request and no spinner.
  • Last page: known from hitCount and the pages fetched — Next disables when nextCursorMark stops advancing or the count is exhausted.
  • New query: a different query is a new queryKey, so the cache, pointer and cursor history reset together. No stale page can survive a query change.
The hook, in outlineuseArticleSearch

hooks/useArticleSearch.ts — outline

function useArticleSearch(query: string) {
  const q = useInfiniteQuery({
    queryKey: ["articles", query],
    queryFn: ({ pageParam }) => searchArticles(query, pageParam ?? "*"),
    initialPageParam: "*",
    getNextPageParam: (last) => last.nextCursorMark ?? undefined,
    enabled: query.trim().length > 0,   // no request for an empty query
  });

  const [page, setPage] = useState(0);
  const next = () => { if (page === q.data.pages.length - 1) q.fetchNextPage(); setPage(p => p + 1); };
  const prev = () => setPage(p => Math.max(0, p - 1));  // cache hit, no fetch

  return { results: q.data?.pages[page]?.resultList.result ?? [],
           status: q.status, page, hasPrev: page > 0, hasNext: /* …count/cursor check */, next, prev };
}

The outline is the contract, not the final code — it shows that forward fetch, backward-by-pointer, the empty-query guard and the per-query reset all fall out of the library plus one small piece of state.

05

Query builder

Half A

The builder holds an ordered list of terms. Each term after the first carries the operator that joins it to what came before. Two pure functions turn that list into the string the user sees and the string the API receives — the same source, two renderings.

article-search.types.ts

type Operator = "AND" | "OR" | "NOT";
type Term = { id: string; value: string; op: Operator | null };  // op is null on the first term only
Term list → two strings
terms[]["cancer", AND "immunotherapy", NOT "melanoma"]The ordered source of truth.
→
displaycancer AND immunotherapy NOT melanomaShown live under the input, announced via aria-live.
api querycancer AND immunotherapy NOT melanomaURL-encoded, sent as query.

For this prototype the display and API strings are the same literal boolean form the brief shows. Keeping them as two functions over one source means either can change later (quoting a phrase, parenthesising an OR group) without touching the other.

  • Add pushes a term with the chosen operator; the first term's operator is null. Enter adds without reaching for the button.
  • Remove drops a term by id; if the first is removed, the new first term's operator is cleared so the string never starts with an operator.
  • Edit the operator in place — each chip after the first exposes a segmented AND / OR / NOT control, so a search is re-shaped without deleting and re-adding terms.
  • Empty list renders an empty query and the results panel shows its resting state — no request is made.
Interaction design

The operator is a segmented toggle (a labelled radio group), not a dropdown, so the three choices are visible and one click. The assembled query shows as live chips with tinted operators; a visually-hidden canonical string carries the same query to assistive tech and to tests. On a blank slate, three example queries (including the brief's own cancer AND immunotherapy NOT melanoma) load with one click, so the first search is never a cold start.

Edge rules the builder guaranteesinvariants
  • The query string never begins or ends with an operator.
  • Removing the only term returns to the empty resting state, not a broken query.
  • A phrase with spaces is treated as one term, not split into two keywords.
  • Whitespace-only input is rejected before it becomes a term.

These are exactly the cases the unit tests in section 08 cover, because they are where a naive join breaks.

06

State & data flow

Runtime

Four pieces of state, each owned in one place: the term list, the server cache and status (TanStack Query), the page pointer (the search hook), and the URL, which mirrors the query and page so a search is shareable. Nothing global, no store.

One search, end to end
1 · inputUser edits termsReducer updates the term list.
→
2 · derivebuildApiQuery(terms)Pure, memoised.
→
3 · fetchuseInfiniteQueryKeyed on the query string; dedupes and caches.
→
4 · pagepointer picks a pagePrev reads cache; Next may fetch.
→
5 · renderStatusView / ResultsListDriven by status + current page.

The four render states

loadingRequest in flight. Skeleton rows + a polite "Searching…" announcement.
success · resultsThe ruled result list for the current page, with pagination.
success · emptyZero hits. A designed empty state naming the query and suggesting a change.
errorNetwork or non-2xx. Plain message + a Retry that refetches.

A fifth resting state — no query yet — shows what the workspace does and invites the first term, so the first frame is never a blank shell.

Why status comes from the query, not from hand-rolled flagsasync handling

A naive version keeps isLoading, error and data as separate useState values and risks them drifting out of sync — a spinner left on after an error, a stale result shown under a new query. Deriving the render state from the query's single status (pending / error / success) makes those contradictions unrepresentable. The empty state is success with zero results, kept distinct from the loading and error states. This is the clearest reason TanStack Query earns its place for even one endpoint.

URL as shareable state

The brief does not ask for it, but a research search is the textbook case for URL state: a researcher who finds a useful result set wants to bookmark or send the link. So the query terms and the current page live in the URL, and a shared link restores the exact search.

What is synced

The term list, encoded so chips and operators restore exactly (?terms=cancer~AND:immunotherapy~NOT:melanoma), and the page as a 1-based &page=N.

How

useUrlState reads the initial state once on mount and mirrors every change with history.replaceState — no router dependency, no history spam.

Deep page restore

The cursor is forward-only, so a restored page=3 is reached by walking the cursor forward until that page is loaded, then landing on it (or on the last available page if the target is beyond the results).

Why encode terms, not the flat query stringdecision

The flat query (cancer AND immunotherapy) would be prettier in the URL, but restoring it means re-parsing a boolean string back into chips — lossy and fiddly to edit. Encoding the structured term list instead means the builder restores to the exact same editable chips the user left, which is the state that actually matters. The encode/decode pair is pure and unit-tested on its own.

07

Accessibility

Built in

Accessibility is in the brief's requirements, not an afterthought. The result list is a record surface, so it has to be navigable and announced, not just visible.

Query builder
Labelled input and operator control. Each term chip has an accessible remove button with a name like "Remove melanoma".
Live query
The constructed query sits in an aria-live="polite" region, so screen readers hear it change as terms are added.
Results
An ordered list of articles. Each title is a real link to the article. Result count and page position announced on change.
States
Loading, empty and error are announced through a status region; errors use role="alert" so they interrupt politely.
Keyboard
Everything operable without a mouse; visible focus rings; pagination buttons disable rather than vanish at the ends.
Reduced motion
prefers-reduced-motion respected — skeleton shimmer and chevron rotation stop.
08

Test design

Vitest · RTL · MSW

Depth placed where the brief points — query construction, results navigation, API failure — rather than spread thin for a coverage number. The layering in section 03 is what makes each of these cheap to test. The network is mocked with MSW, so no test touches the real endpoint.

TargetLevelWhat it proves
Query constructionunitPure buildApiQuery / buildDisplayQuery: AND/OR/NOT joins; add; remove; remove-first clears the leading operator; single term; empty; phrase kept whole.
Results navigationcomponentNext advances a page and requests the next cursor; Previous returns to a cached page with no refetch; buttons disable at the ends.
API failurecomponentA mocked rejected / non-2xx fetch renders the error state, announces it, and Retry issues a fresh request.
URL stateunit + integrationTerms encode/decode round-trips; the hook reads terms + page from the URL and writes them back; a shared link restores the exact search on load.
How the network is fakedMSW

MSW intercepts the request at the network level and returns fixed fixtures — a page with results, an empty page, a 500 — so no test touches the real endpoint. The server runs with onUnhandledRequest: "error", so any un-mocked request fails the test loudly. Navigation tests count the intercepted requests, which is what distinguishes a cache hit on Previous from a refetch on Next.

Deliberately not tested: exhaustive operator permutations, visual styling, and the live API itself. The brief values thoughtful prioritisation over unnecessary coverage; what's left out is written down rather than left silent.

09

Decisions & trade-offs

ADR

The calls I made, each with the reason and the alternative. These are the things the follow-up interview is most likely to probe, so each is stated plainly.

Framework
React + TypeScript + Vite.Matches the role ("React, Vue or equivalent"), the stack I'm fastest and most careful in, and an instant Vite dev loop. TS makes the API response shape a contract the components can rely on.
Architecture
Feature-Sliced Design + Tailwind, per my team standard.Even for one screen I follow the same conventions I build production apps with — FSD folders, Tailwind with brand tokens, an @icons proxy, meemaw, strict no-any, inline errors, MSW. Nesting stays shallow because there is one feature. It costs little to start this way and shows how I actually work, which is what the exercise is probing.
Data
TanStack Query, useInfiniteQuery.Its cursor model fits a forward-only API exactly, and it turns loading/error/empty into one derived status. For a single endpoint it is close to the minimum that still handles cursors and caching correctly — and it backs the Prev-without-refetch behaviour.
Paging
Forward fetch + page pointer over the cache.The API has no previous cursor, so backward navigation is a client concern. A pointer over cached pages gives instant Prev and avoids re-fetching pages already seen.
Rejected
No Redux or global store.Local component state plus the query cache cover everything. A store would be the "unnecessary complexity" the brief warns against, and harder to explain than it's worth here.
Rejected
No infinite scroll.The library supports it, but the brief asks for discrete pages of 25 with next/previous. Discrete paging is also easier to make accessible and to reason about.
URL state
Query and page live in the URL.Beyond the brief, but a search a researcher can bookmark or share is exactly the usability the evaluation rewards, and it matches my team's rule to put search terms in the URL. Done with URLSearchParams + replaceState, no router.
Layout
Results scroll in their own pane.The screen is a fixed-height workspace: masthead and query builder stay put while the results list scrolls internally, so paging and the query stay in view instead of the whole page scrolling.
Scope
Facets & sort are stretch goals.Not asked for by the brief. The core query-builder, results, states and tests ship first; filters are added only if time remains.

Known limitations, written down not hidden

  • Deep paging is forward-only by nature; jumping to page 40 means walking there. Acceptable for a search workflow where users refine rather than skip ahead.
  • No query validation UI beyond empty-guarding — the API accepts loose input, so the builder trusts the user's terms.
  • Lite fields only — no abstract or author affiliations until a detail view is added (noted as a stretch).

The brief, in my words

Build a prototype Research Search Workspace on the Europe PMC Articles REST API, for a researcher who wants to build and refine a literature search without learning query syntax.

Two halves

A · Query builder

Assemble a query visually

Enter a keyword or phrase. Combine terms with AND / OR / NOT. Show the resulting query as it is constructed. Remove terms and refine.

B · Results explorer

Read and page the results

Fetch matching publications. Show title, authors, publication year and a link to each article. 25 per page with next / previous. Handle loading, empty and error states, accessibly.

What they are actually assessing

Functional correctness, maintainable component structure and clear state management, async handling, tests for the behaviours that matter, and — stated twice in the brief — how I prioritise. Their words: “a well-reasoned, partially completed solution is preferable to a feature-complete application that you cannot explain or maintain.” There is a follow-up interview where they walk through the code and may ask for a live change, so everything here has to be explainable and mine.

02

How the API works

Verified against the live endpoint, not recalled. The findings here drive the architecture that follows.

Base: GET https://www.ebi.ac.uk/europepmc/webservices/rest/search — no auth, no backend, CORS-friendly for a browser app.

ParamValueNote
querycancer AND immunotherapy NOT melanomaBoolean operators are applied literally. Hit count fell from 5.6M to 280K once AND/NOT were added, so they really filter.
formatjson—
pageSize25Matches the brief.
cursorMark* then nextThe pagination mechanism. See below.
resultTypelite / corelite gives title, authorString, pubYear, id, source — enough for the list. core adds authorList and abstract if a detail view is added later.
The decisive finding — pagination is forward-only

The response returns a nextCursorMark. To get the next page you resend the request with cursorMark=<that value>. There is no previous cursor and no page/offset parameter — the API only moves forward. So “previous” navigation has to be built on the client by remembering the cursor marks we have already seen. This is the single most important design decision in the task, and exactly the kind of technical judgement they are scoring.

Other verified behaviours

Total count

hitCount gives the total, so we can show “about N results” and know when the last page is reached.

Article link

Build https://europepmc.org/article/{source}/{id} from each result — e.g. MED/42888301.

Error reality

The API is lenient: an empty query and a malformed query both return HTTP 200. So real failures come from the network — fetch rejection, non-2xx, timeout — not from bad input. The error state and its test are built around that, not around the API rejecting a query.

# Verified request — page one
GET /europepmc/webservices/rest/search?query=cancer+AND+immunotherapy+NOT+melanoma&format=json&pageSize=25&cursorMark=*

# Response (trimmed)
{ "hitCount": 280474,
  "nextCursorMark": "AoIIQEV1pCg1Njk3NTY2Nw==",   // feed this back to get page two
  "resultList": { "result": [ { "id", "source", "title", "authorString", "pubYear", "doi", "pmid" } ] } }

04

Architecture

A small, flat structure. Each decision below is one I can defend in the walkthrough.

Query builder state

useReducer over a list of terms, each with its operator. Pure functions turn the term list into the display string and the API query string — these are unit-tested in isolation.

↓ query string
Data layer — TanStack Query

useInfiniteQuery keyed on the query. getNextPageParam returns nextCursorMark — the library is built for exactly this cursor shape. It gives caching, loading and error status and request dedupe for free.

↓ cached pages + a page pointer
Pagination

The API is forward-only, so “Next” fetches the next cursor page and “Previous” just moves a page pointer back to an already-cached page. Backward navigation with no backward API — resolved by the cache.

↓ current page of 25
Presentation

Results list of ruled record rows; status-driven loading / empty / error views; the query builder panel. Presentational components take data as props and stay testable.

Key decisions

React + TS

Matches the job (“React, Vue or equivalent”) and is the stack I am fastest and most careful in. Vite for an instant dev loop and a clean build.

TanStack Query

Turns forward-cursor paging, caching and the loading/error states into configuration rather than hand-rolled effects. For a single endpoint it is close to the minimum that still handles cursors well.

No Redux

Local component state and the query cache cover everything. A global store would be the “unnecessary complexity” the brief warns against.

Pure query functions

Term-list → display string and → API string are pure and separately tested, so the builder’s logic is verified without rendering anything.

Design & brand

The prototype should read as if it belongs to Europe PMC. The approach: borrow a proven structure from my own design shelf, then dress it in EMBL-EBI’s real brand — read from their live stylesheets, not matched by guesswork.

The brand, from EMBL-EBI’s own CSS

EMBL’s web typeface is IBM Plex Sans with IBM Plex Mono for identifiers (122 font declarations across ebi.ac.uk and embl.org). The service accent is EBI Petrol; links are EMBL blue; “free full text” status is EMBL green. Light theme throughout, dense and institutional, results rendered as a plain ruled list rather than heavy cards.

The structure we borrow

The base is my Ìbejì system, whose organising law is “territory versus record”: record surfaces are ruled rows in IBM Plex Mono with no ornament. A literature result list is a record surface — ruled rows of titles, authors, identifiers and years — so the fit is structural, not cosmetic. We keep that record idiom and recolour its teal to EBI Petrol; we drop its ceremonial serif, since EMBL’s chrome is pure Plex Sans. The result is a workspace that looks native to Europe PMC while standing on a system I can explain end to end.

A single result row

Title as a blue/petrol link in slightly heavier weight · authors on one muted grey line · journal and year muted beneath · a links row carrying the article link, PMID and DOI in IBM Plex Mono · thin hairline separators, no boxed cards. This mirrors how Europe PMC itself lays out results.

Light theme only — EMBL’s web surface is light, and it matches the standing preference.

Testing

Vitest with React Testing Library. Depth placed where the brief points, not spread thin.

WhatHowWhy it matters
Query constructionUnit tests on the pure term-list → string functions: AND/OR/NOT, add, remove, single term, empty.The builder’s core logic, named by the brief.
Results navigationComponent test: next advances a page and requests the next cursor; previous returns to a cached page without a refetch.Proves the forward-cursor-plus-cache design works.
API failureMock a rejected / non-2xx fetch and assert the error state renders and is announced.The real failure mode, since the API accepts bad queries.

Not every edge case — the brief explicitly values thoughtful prioritisation over exhaustive coverage. What is left out is written down in the docs rather than left silent.
